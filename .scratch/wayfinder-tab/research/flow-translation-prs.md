# Translation changes and Jira linkage in DoctrinAB/flow

**Context:** Research for [henceiam/devman#5](https://github.com/henceiam/devman/issues/5), under the Translation progress monitoring page Wayfinder. This records representation and linkage evidence only; it does not decide product scope (tracked separately in dependent issue #4).

## Findings

- **`flow` consumes translation keys but does not appear to own the main translation catalogue.** Its phrases API routes call a phrases service; an inline example points to locale JSON in the separate `DoctrinAB/translations` repository (`applications/admin2-app/src/server/api/phrases.js`, [source](https://github.com/DoctrinAB/flow/blob/master/applications/admin2-app/src/server/api/phrases.js#L9-L16)). Thus application code changes can use keys, while translation-key/value edits are represented in the translations repository's JSON files.
- **The translations repository distinguishes key changes from value/content changes.** Its labels define `translations-keys-update` for adding, removing, or updating keys and separate labels for translation-value updates (`.github/labels.yml`, [source](https://github.com/DoctrinAB/translations/blob/master/.github/labels.yml#L13-L26)). A content-check workflow watches locale JSON paths and skips PRs labeled `translations-keys-update` (`.github/workflows/ai-check-translations-content.yml`, [source](https://github.com/DoctrinAB/translations/blob/master/.github/workflows/ai-check-translations-content.yml#L1-L30)).
- **A PR branch can link a `flow` change to an EBBACKLOG Jira ticket through automation.** The `flow` workflow extracts `EBBACKLOG-\d+` from the head branch name and prepends that key to the PR description when a PR opens (`.github/workflows/update-description-with-jira-ticket.yml`, [source](https://github.com/DoctrinAB/flow/blob/master/.github/workflows/update-description-with-jira-ticket.yml#L1-L28)). This is the strongest directly evidenced PR-to-ticket signal found for `flow`; it depends on the branch following that naming pattern.
- **A translation key can be associated with a Jira ticket through the ticket's `Translation keys` field, but not by an observed automatic diff-to-ticket mechanism.** The `flow` Jira skill documents `customfield_11285` as the ticket's translation-key mapping (`.agents/skills/jira/SKILL.md`, [source](https://github.com/DoctrinAB/flow/blob/master/.agents/skills/jira/SKILL.md#L12-L16)). Comparing an edited key to a populated field can therefore provide a key-to-ticket match, but the sources reviewed do not establish that this field is automatically synchronized from a PR or translation JSON diff.
- **Translation PR title linkage is documented as a convention, not a verified enforcement.** The translations PR template gives a `SUPPORT-1234: ...` merge-title example and asks for affected environments/locales (`.github/pull_request_template.md`, [source](https://github.com/DoctrinAB/translations/blob/master/.github/pull_request_template.md#L1-L20)). The reviewed description-validation workflow checks the PR body sections, not the Jira key convention (`.github/workflows/validate-pr-description.yml`, [source](https://github.com/DoctrinAB/translations/blob/master/.github/workflows/validate-pr-description.yml#L1-L170)).

## Limits

The branch-name automation is specific to `EBBACKLOG-` in `flow`; the translations template example instead uses `SUPPORT-`. The reviewed sources do not verify a Jira integration that discovers translations-repository PRs, nor do they show automated links from individual changed keys to tickets. Those links should not be treated as reliable unless the PR carries an enforced ticket reference or the matching Jira field is populated.
